# SKYSENSE — ESP32 Hardware Integration Guide

This document is the single reference for connecting the physical ESP32
environmental station to SKYSENSE later. It is written so you can return after
building the hardware and follow the steps without re-discovering the codebase.

## 1. Current state: Simulation

- The ESP32 does **not** exist yet and is **NOT connected**.
- The entire product (Home, Analytics, AI, Alerts, Devices) runs on a
  deterministic **simulation** generated by `apps/web/src/lib/environmental/mockData.ts`
  and served through the data-provider abstraction in
  `apps/web/src/lib/environmental/provider.ts`.
- The Devices page explicitly says **Simulation Mode** and **"Hardware is not
  connected."** — this must remain true until real hardware reports in.
- Connection state is **heartbeat-derived**: a device is NEVER reported
  `online` unless it has actually reported telemetry (each accepted POST also
  records a heartbeat/last-seen). Simulation devices have **no** heartbeat, so
  they always render as Simulation Mode / Not Connected. See §4b.

## 2. Future state: ESP32

```
ESP32
  ↓  POST /api/devices/SKY-ESP32-001/data  (JSON telemetry)
  ↓  device verification (registered device)
  ↓  validation (sensor contract)
  ↓  storage (Firestore raw readings)
  ↓  EnvironmentalData (canonical model)
  ↓  Analytics / AI / Alerts / UI
```

The data layer hides whether the source is simulation or hardware. When the
ESP32 provider is activated, **no page or analytics/AI/alert module changes**.

## 3. Device identity

| Field          | Value            |
| -------------- | ---------------- |
| Device ID      | `SKY-ESP32-001`  |
| Device name    | `SKYSENSE ESP32 Environmental Station` |
| Location       | `Ahmedabad, India` |

Device IDs MUST match the pattern `SKY-ESP32-###`. Only registered devices are
accepted. To register another station, add it to
`apps/web/src/lib/devices/registry.ts` (server-side registry).

## 4. Ingestion endpoint

| Method | Path | Purpose |
| ------ | ---- | ------- |
| POST   | `/api/devices/:deviceId/data` | Submit one reading |
| GET    | `/api/devices/:deviceId/data` | Latest stored reading |
| GET    | `/api/devices/:deviceId/data/latest` | Latest stored reading |
| GET    | `/api/devices/:deviceId/data/history` | Stored readings, newest first |
| GET    | `/api/devices/:deviceId/status` | Device status |

### Storage layer

- Raw readings are stored at `deviceReadings/{deviceId}/readings/{id}` (a
  subcollection, so no composite index is needed) via
  `apps/web/src/lib/devices/storage.ts`, which persists through the
  **Firebase Admin SDK** (`packages/api/src/admin.ts`) with a trusted server
  identity. The browser web SDK (`@skysense/api`) remains the client path for
  user auth/profiles and never touches `deviceReadings` — browser and server
  persistence are separate. Derived analytics/AI data is never stored here.
- Heartbeats are stored at `deviceReadings/{deviceId}/heartbeat/latest`
  (same subcollection layout, one doc per device) via
  `saveDeviceHeartbeat` / `getDeviceHeartbeat` in the same module. A heartbeat
  is written for **any accepted** telemetry (even all-`null` placeholders) and
  records the **server receipt time** as `lastSeenAt` — never the device clock.
- `deviceReadings` is **deny-by-default in Firestore rules** for all clients.
  The Admin SDK bypasses rules, so persistence needs no rule change; the server
  is the enforcement point for the device token.
- The storage code is fully wired. In this repo a real write/read was verified
  against the local Firestore **emulator** (`FIRESTORE_EMULATOR_HOST`, see
  `firebase/firebase.json`). To persist to the real `skysense-5084d` Firestore,
  provision one of the server-side credentials in `apps/web/.env.example`
  (recommended: `FIREBASE_SERVICE_ACCOUNT` with a downloaded service-account
  key — server env only, never committed, never `NEXT_PUBLIC_`). Until a
  credential is provisioned, the API honestly reports `stored: false,
  pendingStorage: true` (POST) and 503 (GET) with the missing-credential
  detail — never a fake stored reading.

### 4b. Heartbeat & connection states

Implemented in `apps/web/src/lib/devices/heartbeat.ts` (server-side only —
never imported by browser page code):

| State          | Meaning                                                              |
| -------------- | -------------------------------------------------------------------- |
| `not_connected`| No heartbeat has ever been recorded for this device.                 |
| `online`       | Heartbeat received within the STALE threshold (default **5 min**).   |
| `stale`        | Heartbeat older than STALE but within OFFLINE (default **15 min**).  |
| `offline`      | Heartbeat older than OFFLINE.                                        |
| `simulation`   | No heartbeat at all and the device is the simulated station.         |

- Thresholds are server env vars: `SKYSENSE_DEVICE_STALE_AFTER_MS`
  (default `300000`) and `SKYSENSE_DEVICE_OFFLINE_AFTER_MS` (default `900000`).
- `GET .../status` derives `connection`/`operatingMode` from the stored
  heartbeat (`lastSeen`, `firmwareVersion`, `sensorCount`,
  `healthySensorCount`). With no heartbeat it returns `not_connected` /
  `simulation` and never claims hardware is live.

## 5. JSON payload format (POST)

```json
{
  "deviceId": "SKY-ESP32-001",
  "timestamp": "2026-08-16T12:34:56.000Z",
  "temperature": 34.2,
  "humidity": 51,
  "pressure": 1008.6,
  "airQuality": 66,
  "uvIndex": 8.8,
  "windSpeed": 10.5,
  "windDirection": 135,
  "rainfall": 0,
  "firmwareVersion": "skysense-fw-0.1.0",
  "battery": 84
}
```

Rules:

- `deviceId` and `timestamp` (ISO-8601 UTC) are **required**.
- `timestamp` must be plausible: a timestamp more than **5 minutes in the
  future** (relative to the server clock) is rejected with HTTP 400, preventing
  a mis-configured device clock from producing "online" states forever.
- Every sensor field may be a **number within its valid range**, or
  **`null`/absent** meaning "this sensor is not reporting". A `null` is
  **never** converted to zero.
- An all-`null` payload (hardware placeholders) is accepted and acknowledged
  but **not persisted**.
- Fields outside the schema / out-of-range values are rejected with HTTP 400
  and a clear error list — invalid data never reaches Analytics/AI/Alerts.

## 6. Sensor registry & placeholder hardware components

Configured in `apps/web/src/lib/devices/sensors.ts`. The `hardwareComponent`
strings are **software placeholders**, not physical part numbers:

| Sensor key       | Placeholder component         | Unit    | Range        |
| ---------------- | ----------------------------- | ------- | ------------ |
| temperature      | `ESP32_TEMPERATURE_SENSOR`    | °C      | -40 – 60     |
| humidity         | `ESP32_HUMIDITY_SENSOR`       | %       | 0 – 100      |
| pressure         | `ESP32_PRESSURE_SENSOR`       | hPa     | 800 – 1100   |
| airQuality       | `ESP32_AIR_QUALITY_SENSOR`    | US AQI  | 0 – 500      |
| uvIndex          | `ESP32_UV_SENSOR`             | index   | 0 – 20       |
| rainfall         | `ESP32_RAIN_SENSOR`           | mm      | 0 – 1000     |
| windSpeed        | `ESP32_WIND_SPEED_SENSOR`     | km/h    | 0 – 200      |
| windDirection    | `ESP32_WIND_DIRECTION_SENSOR` | degrees | 0 – 360      |

Each sensor also has `enabled` (all `true` in simulation) and a `description`.
Disable a sensor here if the physical build omits it.

> Embedded firmware (ESP32 code) lives in a **separate project**. The physical
> GPIO / I2C / SPI / UART wiring for the components above is defined there,
> **not** in this Next.js application. This web app only defines the software
> field → component mapping.

## 7. Where the future ESP32 credential goes

- **Placeholder:** `apps/web/src/lib/devices/deviceAuth.ts`.
- **Server env var:** `SKYSENSE_ESP32_DEVICE_SECRET` (see `apps/web/.env.example`).
- The firmware sends the secret in the header `x-skysense-device-token`.
- When the env var is **set**, the ingestion API requires a matching token
  (HTTP 401 otherwise). When it is **unset** (today), the API reports
  `deviceAuth: { enforced: false, verified: false }` and never claims the
  device is authenticated.
- **Never** commit the secret; provide it only through the server environment.

## 8. How to switch from simulation to real hardware

1. Build the ESP32 station; wire the sensors (separate firmware project).
2. Firmware POSTs telemetry to `/api/devices/SKY-ESP32-001/data` with the
   schema above (all 8 values or the subset physically present).
3. Provision `SKYSENSE_ESP32_DEVICE_SECRET` server-side and put the matching
   value in firmware.
4. Implement `Esp32DataSourceProvider` (declared in
   `apps/web/src/lib/environmental/provider.ts`) that reads stored readings
   (via `apps/web/src/lib/devices/storage.ts`) and maps them to
   `EnvironmentalReading[]`, then register it with
   `setEnvironmentalDataProvider(...)`.
5. The provider's readings carry `dataSource: "esp32"`,
   `connectionMode: "online" | "offline"`, `firmwareVersion`, `sensorStatus`,
   and the real `location` — the rest of the product adapts automatically.

## 9. What must NOT change when hardware is connected

- The canonical `EnvironmentalReading` shape in
  `apps/web/src/lib/environmental/types.ts`.
- The `AnalyticsResult` contract, the AI `AIAnalysis` contract, or the alert
  engine (`apps/web/src/lib/intelligence/*`, `apps/web/src/lib/alerts/*`).
- The Analytics / AI / Alerts / Devices page components and the design system.
- The validation boundary (`apps/web/src/lib/devices/validation.ts`) — keep it
  rejecting invalid data before it reaches the pipeline.
- Raw readings must stay separate from derived analytics/AI data
  (`deviceReadings/{deviceId}/readings` holds only raw values; derived data is
  computed on demand and stored nowhere as if it were a raw reading).
- Heartbeat/status honesty: `GET .../status` must keep deriving state from the
  real stored heartbeat and must never claim `online`/`live` without one.
  `heartbeat.ts` stays server-side (browser code reads snapshots, not storage).
- The Devices page keeps showing **Simulation Mode** until a real heartbeat
  exists; the "Hardware is not connected" note stays visible in simulation.

## 10. Verification checklist after implementation

- `/devices` still shows **Simulation Mode** and "Hardware is not connected."
- `GET .../status` before any POST → `not_connected`, no `lastSeen`.
- `POST` valid payload → 200 (`stored: true`, `heartbeat: { recorded: true }`);
  `GET .../status` then shows `online` / `live` with `lastSeen`, firmware and
  healthy-sensor counts. Malformed → 400; unknown deviceId → 400;
  future-dated timestamp → 400; all-null payload → 200 (`stored: false`,
  heartbeat still recorded).
- `GET .../data/latest`, `.../data/history` return stored readings once data
  flows; `/status` reports Simulation Mode until the ESP32 provider is active.
- Setting `SKYSENSE_DEVICE_STALE_AFTER_MS`/`SKYSENSE_DEVICE_OFFLINE_AFTER_MS`
  shifts when a device is reported stale/offline.
